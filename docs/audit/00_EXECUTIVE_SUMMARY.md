# FlowRev Phase 0 監査 — エグゼクティブサマリー（非エンジニア向け）

対象コミット: `2e2861aed27fd5287fd0aacfcb57c5df90f03a3` (branch: `claude/flowrev-phase-0-audit-fpgr8e`)
調査日: 2026-07-31

## 結論を一言で

**FlowRevの中核機能（顧客管理・商品管理・LP生成・決済・会員サイト）は実際に動くコードとして存在しており、「作っただけで動かないハリボテ」ではありません。** ただし、そのまま外部公開すると**決済詐欺・なりすまし・管理画面の乗っ取りにつながる重大なセキュリティ欠陥が複数あります。** これらを直さないままの本番公開は推奨できません。

## 今、何ができるか

- 管理者/クライアント/カスタマーのログインとロール分け（システム管理者 → 代理店 → クライアント → 顧客の4階層）
- 顧客の登録・一覧・削除
- 商品の登録・編集
- **LP（ランディングページ）のAI自動生成・編集・プレビュー・公開** — これが最も作り込まれている機能です
- LPからの顧客登録（自己登録フォーム）
- AIによる文章生成（商品説明・フォローメール文）、AIによる画像生成
- 画像アップロード（Supabase Storageへ保存）
- Stripe決済（クライアントごとに個別のStripeキーを設定可能）
- 購入者向け会員サイト（動画講座、進捗管理）
- メール送信（Resend経由）

## 今、何ができないか / 動かないか

- **契約管理**：該当する機能はコード上に一切存在しません。
- **Onbizu連携・CommitRev連携**：コード上に一切存在しません（未着手）。
- **LINEのWebhook受信**：存在しません。そのため「顧客がLINE友だち登録した」という情報をシステムが受け取る手段がなく、LINE送信機能自体はコードとしてあってもLINE経由で顧客とつながることが実質できません。
- **フォローアップの自動送信（購入後フォロー・未行動者へのステップメール）**：仕組み（DB・ロジック）はできていますが、**定期実行の仕組み（Cron）に繋がっていない**ため、スタッフが手動でボタンを押さない限り、実際には1通も自動送信されません。
- **プラン管理（本部/システム管理者側）**：新規作成はできますが、編集・削除ができません。

## 今すぐ利用可能か

**いいえ。** コード自体は多くの機能について実用レベルまで作り込まれていますが、下記「最も大きな問題」を解消しないまま実運用（実際の決済・実際の顧客データ）に投入するのは危険です。開発中の検証・デモ用途であれば現状でも動作します。

## 最も大きな問題（優先度順）

1. **【最重要】Stripe決済のなりすましが可能**：クライアントがWebhook用の「署名シークレット」を設定していない場合、誰でも「支払いが完了した」という偽の通知を送りつけることができ、**お金を払わずに商品・講座へのアクセス権を取得できてしまいます。** 現状、この設定は必須になっていないため、見落としが起きやすい状態です。
2. **【最重要】管理画面がハッキングされうる（стored XSS）**：AIが生成したLPのHTMLを、管理者が「新しいタブでプレビュー」した瞬間に、悪意あるスクリプトが管理画面と同じ権限で実行されてしまう経路があります。改ざんされたAI出力や、悪意ある担当者・乗っ取られたアカウントが起点になり得ます。
3. **【重大】権限チェック漏れにより、一般顧客が全テナントに一斉メール送信できてしまう**：フォローアップメール送信の内部エンドポイントに、ログインしているかどうかのチェックしかなく「管理者かどうか」のチェックが抜けています。最も権限の低い「顧客」アカウントでも、全クライアントの未送信メール・LINEメッセージを今すぐ全部送らせることができてしまいます。
4. **不正利用への対策（レート制限）が皆無**：ログイン試行にもAI生成機能（課金対象のOpenAI/Anthropic API呼び出し）にも回数制限がなく、悪用されると高額請求や不正ログイン試行につながります。
5. **データベースのスキーマ管理が手作業**：正式なマイグレーション管理の仕組み（Drizzle/Supabase Migrations）を使っておらず、SQLファイルをSupabaseの管理画面に手でコピペする運用です。しかも、**手順書が想定していない重複・矛盾したSQLファイルがリポジトリに残っている**ため、手順を誤ると壊れたスキーマができる恐れがあります。

## なぜ修正が必要か

上記の問題は「機能が足りない」ではなく「**お金が絡む部分・他社データが見える可能性がある部分**」に集中しています。マルチテナントSaaS（複数の会社の情報を1つのシステムで扱う仕組み）として顧客に提供する以上、これらは信頼性の根幹に関わります。幸い、**データベースのテナント分離（RLS）自体はかなりしっかり作られている**ため、土台は健全です。問題は「入口（Webhook・API認可）」に集中しており、範囲を絞った修正で対応可能です。

## 次に何をするべきか

1. まず `docs/audit/05_SECURITY_FINDINGS.md` のCritical/High項目を修正する（Stripe Webhook検証・LP管理画面のXSS・scenarios/execute権限漏れ）。
2. 次に `docs/audit/07_MIGRATION_PLAN.md` に従って、GitHub Actionsでのtypecheck/build確認、DBマイグレーション方式の統一、Vercel環境変数の整備を進める。
3. 機能拡張（LINE Webhook実装、フォロー自動送信のCron化など）はセキュリティ修正の後に着手する。

詳細は各セクションの調査資料（`docs/audit/01`〜`08`）を参照してください。
