# Phase 3a 着手可否の判断

- **判断日**: 2026-08-03
- **基準コミット**: `3bf43c4`

---

## 1. 判断

## **条件付きで進める**

Phase 3a（機能制御）の**設計・実装に着手してよい**。ただし **Phase 2 を「本番利用可能」と宣言し、実顧客の決済を受け付けることは、§2 のブロッカーが解消するまで行わない。**

理由は、残っているのが**コードの欠落ではなく実環境での確認作業**だからである。確認作業はPhase 3aの実装と並行して進められ、互いに待ち合わせる必要がない。一方、確認が済んでいない導線に実顧客を通すことは、Phase 3aの進捗とは無関係にリスクとして残る。

## 4. Phase 3a に進んでよいと判断した根拠

Phase 3a（機能制御）は、プランに応じて機能の可否を切り替える仕組みである。これが乗る土台として以下が揃っている。

| 土台 | 状態 |
|---|---|
| テナント階層（クライアント→OEM→HQ）の設定解決 | LINE・Stripe・AI・Cloudflare・メールの5サービスで統一済み |
| テナント境界の書き込み保護 | `wl-tier-writes.test.ts`（11件）で他OEM行・HQ行・配下クライアント行を書き換えないことを検証 |
| 顧客のテナント所属 | `inviteCustomerWithTenant()` に集約。有料・無料の両導線が同じ経路を通る |
| プラン情報の参照 | `getClientPlanFeatures()` / `hasFeature()` が既に `app/(dashboard)/layout.tsx` のナビ制御で稼働している |
| 自動テスト基盤 | 9ファイル / 70件。各テストは実装を壊して失敗することを確認済み |

特に最後の点が重要で、Phase 3a は「特定のプランで特定の機能が**見えない／使えない**」という**否定形の要件**を多く含む。否定形は正常系のテストでは検出できず、実装が空振りしていても画面上は正しく見える。この種の失敗を捕まえる仕組みが既に動いていることが、着手してよいと判断する主な根拠になっている。
