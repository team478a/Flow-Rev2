# ネイティブ運営機能（Onbizu/CommitRev代替の自社実装）

Onbizu・CommitRevが担おうとしていた「顧客の行動を捉え、未行動者をフォローし、目標達成を伴走する」という概念を、FlowRev内部にネイティブ機能として実装する方針を示す。ここに記載する6機能は、`docs/product/`（ブランチ`feature/phase-1-activity-events-foundation`）の既存設計文書と整合させ、矛盾する場合は`docs/product/`側の詳細設計を優先する。

## 1. 行動イベント（Activity Events）

- **目的**: 顧客の行動（ログイン、動画視聴、教材ダウンロード、フォーム送信等）を横断的に記録し、他の運営機能（未行動検知・進捗管理・フォロー自動化）の基盤データとする。
- **主な利用者**: システム内部（他機能から参照）。直接の閲覧者はclient_owner（顧客ごとの行動履歴として）。
- **MVPスコープ**: `docs/product/ACTIVITY_EVENT_CATALOG.md`で定義済みのイベント種別を土台に、`activity_events`テーブルへの記録経路を実装する。既存の`customers.last_action_at`（死んだ列）はこの実装後に置き換える。
- **必要データ**: `activity_events(id, customer_id, client_id, white_label_id, event_type, metadata, occurred_at)`。テナント列を最初から持つ（`00`章の原則）。
- **既存機能との接続**: `lesson_progress`（視聴完了のみ記録）はイベントの一種として統合可能。将来的に`lesson_progress`のUPDATE時に`activity_events`へも記録する。
- **将来拡張**: イベントベースのセグメンテーション、AI運営アシスタントへの入力。
- **OEM対応**: `client_id`/`white_label_id`をレコードに持たせ、RLSで階層フィルタする。

## 2. オンボーディング

- **目的**: 購入直後の顧客が迷わず最初のアクションを取れるよう、初回フローを自動化する。
- **主な利用者**: customer（体験する側）、client_owner（設計する側）。
- **MVPスコープ**: 購入完了トリガーで固定のオンボーディングメッセージ（メール/LINE）を送る仕組み。既存の`follow_scenarios`（`trigger_type='purchase'`）をそのまま活用できる可能性が高く、新規エンジンは作らない。
- **必要データ**: 既存の`follow_scenarios`/`scenario_steps`で表現可能。新規テーブルは不要と見込む（`06`文書で最終判定）。
- **既存機能との接続**: フォローシナリオエンジン（`app/api/admin/scenarios/execute/route.ts`）をそのまま利用。
- **将来拡張**: 進捗連動の分岐オンボーディング。
- **OEM対応**: `follow_scenarios`は既に`client_id`を持つため階層分離は既存のまま機能する。

## 3. 未行動検知（Inactivity Detection）

- **目的**: 一定期間行動のない顧客を検知し、運営者に提示する。
- **主な利用者**: client_owner（対応する側）。
- **MVPスコープ**: `activity_events`の最終イベント日時を基準に、閾値（例: N日未行動）を超えた顧客を一覧化するバッチ処理・画面。
- **必要データ**: `activity_events`（1章）に依存。専用の追加テーブルは不要見込み（ビュー/クエリで算出）。
- **既存機能との接続**: 検知結果を`follow_scenarios`の新しいトリガー種別（`trigger_type='inactivity'`）として発火できるようにする（`02`文書6章の拡張と対応）。
- **将来拡張**: 未行動理由の推定（AI）。
- **OEM対応**: クエリはテナントIDでスコープする。

## 4. コミットメント管理

- **目的**: 顧客が設定した目標・約束事の進捗を追跡し、達成を後押しする。
- **主な利用者**: customer（自身の目標設定）、client_owner（進捗確認・声かけ）。
- **MVPスコープ**: `docs/product/COMMITMENT_MANAGEMENT_MVP.md`の設計を土台とする。顧客が目標を1件登録し、達成/未達成を自己申告またはclient_ownerが確認する最小フロー。
- **必要データ**: 新規`commitments`テーブル（`customer_id`, `client_id`, `white_label_id`, `title`, `status`, `due_date`等）。
- **既存機能との接続**: コミットメント未達成を`activity_events`の一種として記録し、フォロー自動化のトリガーに使える設計とする。
- **将来拡張**: 複数目標、マイルストーン分割。
- **OEM対応**: レコードに階層列を最初から持つ。

## 5. 購入後フォロー自動化

- **目的**: 未行動検知・進捗停滞・コミットメント未達成等をトリガーに、自動でフォローメッセージを送る。
- **主な利用者**: client_owner（ルール設計）、customer（受け取る側）。
- **MVPスコープ**: 既存`follow_scenarios`の`trigger_type`を拡張（`purchase`のみ→`inactivity`/`commitment_overdue`等を追加）。定期実行のCron/バッチを新設（現状皆無）。
- **必要データ**: 既存テーブルの拡張（`scenario_steps.trigger_type`の許容値追加）で対応可能と見込む。
- **既存機能との接続**: 2章・3章・4章のトリガー源をこのエンジンに接続する。
- **将来拡張**: ビジュアルな条件分岐ビルダー（今回は明示的に後回し）。
- **OEM対応**: 既存の`client_id`スコープをそのまま利用。将来的にOEM機能制御でフォロー自動化の利用可否・段数上限をプラン制御する。

## 6. AI運営アシスタント

- **目的**: 未行動者・優先対応者・解約リスクをAIが要約し、運営者の「今日何をすべきか」を提示する。
- **主な利用者**: client_owner（主）、white_label_owner（配下クライアントの俯瞰、将来）。
- **MVPスコープ**: 1〜4章のデータ（行動イベント・未行動検知結果・コミットメント状況）を要約し、ダッシュボードにテキストで提示する読み取り専用機能。**提案の自動送信は行わない**（`00`章8節の原則）。
- **必要データ**: 既存のAI生成基盤（`lib/repositories/ai-settings.ts`等）を流用。新規テーブルは不要見込み。
- **既存機能との接続**: AI利用量計測（`02`文書13章）と接続し、将来のOEMコスト管理に使う。
- **将来拡張**: 提案→承認→自動送信のワークフロー化。
- **OEM対応**: AI設定解決を3階層フォールバック（`02`文書7章）に統一した上で、テナント単位の利用量を計測する。

## まとめ

上記6機能のうち、**行動イベント・コミットメント管理は新規テーブルが必要**、**オンボーディング・フォロー自動化は既存の`follow_scenarios`エンジンの拡張で対応可能**、**未行動検知・AI運営アシスタントは新規の集計/表示ロジックが中心で新規テーブルは最小限**、という整理になる。これにより「全部新規に作る」のではなく既存資産の再利用度が高いことが分かる。
