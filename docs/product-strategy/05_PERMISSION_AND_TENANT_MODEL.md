## 2. RLS / アプリ層 / service-role の責任分担

| 層 | 責任範囲 |
|---|---|
| RLS（DBレベル） | テナント境界の強制（`white_label_id`/`client_id`/`customer_id`によるSELECT/INSERT/UPDATE/DELETE制限）。既存の`get_user_role()`等のSECURITY DEFINER関数を継続利用し、新規テーブルにも同一パターンを適用する |
| アプリ層（Server Actions / Route Handlers） | 業務ルールの強制（上限クランプ、ステータス遷移の妥当性チェック、招待フローの整合性等）。RLSだけでは表現しづらい「上位テナントの設定を下位が超えられない」等のロジックはここで行う |
| service-role使用箇所 | Webhook処理（Stripe等）、バッチ/Cron処理（未行動検知、フォロー自動化の定期実行）等、ユーザーセッションを介さない処理に限定して使用する。service-role使用箇所は必ずコードコメントで理由を明記し、`docs/audit/`の既存棚卸し方針を継続する |

## 3. テナント解決の一貫性

現状、機能ごとに「自分のテナントIDをどう取得するか」の実装がばらついている（`01`文書7章）。今後追加する機能（行動イベント・コミットメント管理・機能制御・利用量管理・監査ログ）は、必ず`lib/tenant/resolve.ts`（新設想定、`02`文書1章）を経由してテナントIDを取得し、個別実装を増やさない。

## 4. customerロールの扱い

`customer`は他の3ロールと異なり、自身のデータ（購入履歴・進捗・コミットメント）にのみアクセスできる。将来的に顧客自身が自分の行動イベント・コミットメント状況を確認できるマイページ機能を検討する余地はあるが、今回のロードマップでは運営者側（client_owner）の閲覧を優先する。
