# Phase 1 詳細計画: 設定解決パターンの統一

`07_IMPLEMENTATION_ROADMAP.md`のPhase 1を、Claude Code/Codexの1セッションで完結できる粒度のタスクに分割する。`lib/repositories/email-settings.ts:105-149`が持つ「テナント別設定があればそれを使い、なければ上位にフォールバックする」という考え方を参照実装（お手本）とし、他4機能をこれに合わせる。

**（2026-08-02追記、Task 1-1実装時の発見）実際に到達できる階層数はテーブルのテナント列構成によって異なり、一律「3階層」ではない**:
- `ai_provider_settings`（AI設定）・`email_settings`（メール設定）: `white_label_id`列のみで`client_id`列が存在しない。クライアント単位の設定はスキーマ上そもそもあり得ないため、実現できるのは**2階層（WL→HQ）**。`email-settings.ts`の`getActiveEmailSetting()`も実際には2階層。
- `line_accounts`（LINE設定）・`stripe_accounts`（Stripe設定）: `client_id`・`white_label_id`の両列が既に存在する（後者はnullable）。クライアント単位の行に加え、`client_id IS NULL AND white_label_id = X`のWL単位の行、`両方NULL`のHQ単位の行を許容できるため、**3階層（クライアント→WL→HQ）を実現できる**。
- `cloudflare_settings`（Cloudflare設定）: テナント列が一切ない。3階層化には`client_id`・`white_label_id`両方の追加が必要（Task 1-4参照）。

## Task 1-1: AI設定の2階層フォールバック化（WL→HQ）

- **目的**: `getActiveAiSetting()`がHQ行しか見ておらず、WL単位で設定してもクライアントに反映されない不具合を修正する。
- **対象ファイル**: `artifacts/flowrev/lib/repositories/ai-settings.ts`（`33-57`行付近）
- **新規ファイル**: なし
- **DB変更**: なし（既存テーブルに既にWL単位のユニーク制約があるため）
- **実装内容**: `email-settings.ts`の`getActiveEmailSetting(whiteLabelId)`と同じ構造で、WL ID→HQの順に検索する関数に書き換える（`ai_provider_settings`に`client_id`列が存在しないため2階層）。呼び出し元のシグネチャ変更が必要な場合は全呼び出し箇所を洗い出して更新する。
- **テスト内容**: (a) WL単位のAI設定がある場合それが使われる (b) WL単位がない場合HQ設定が使われる、の2パターンを確認。
- **完了基準**: 2パターンとも期待通りの設定が返る。既存のAI生成機能が壊れていない。
- **前提タスク**: なし
- **状態**: 実装完了（PR #3、`feature/phase1-ai-settings-fallback`）。typecheck・build成功。実データでの2パターン確認はdev環境で別途推奨（PR #3参照）。

## Task 1-2: LINE設定の3階層フォールバック化

- **目的**: LINE設定がクライアント単位のみでWL単位・HQ単位のフォールバックがない状態を解消する。
- **対象ファイル**: `artifacts/flowrev/lib/repositories/line-settings.ts`（`47-70`行付近）
- **新規ファイル**: なし
- **DB変更**: なし（`line_accounts`に既に`client_id`・`white_label_id`の両列が存在するため、WL単位・HQ単位の行はそのまま作成できる）。
- **実装内容**: クライアントID→WL ID→HQの順に検索する関数に書き換える（Task 1-1で確立したフォールバック実装パターンをそのまま適用できるが、こちらは実際に3階層に到達する）。
- **テスト内容**: (a) クライアント単位の設定がある場合それが使われる (b) クライアント単位がなくWL単位がある場合それが使われる (c) どちらもない場合HQ設定が使われる、の3パターンを確認。
- **完了基準**: 3パターンで期待通りの設定が返る。既存のLINE配信機能が壊れていない。
- **前提タスク**: Task 1-1（同一パターンの実装経験を踏まえて進める方が手戻りが少ないための順序づけであり、技術的な依存はない）

## Task 1-4: Cloudflare設定の3階層フォールバック化

- **目的**: Cloudflare設定がテナント概念自体を持たず全体で1行のみの状態を、テナント単位に対応させる。**（2026-08-01決定事項）3階層フォールバック（クライアント→OEM→本部）を採用する方針自体は確定済み。本タスクでは既存`cloudflare_settings`テーブルを実際に調査したうえで、具体的なテナント列追加方法を確定する（`09`文書決定事項1参照）。**
- **対象ファイル**: `artifacts/flowrev/lib/repositories/cloudflare-settings.ts`（`60-82`行付近）
- **新規ファイル**: なし
- **DB変更**: `cloudflare_settings`テーブルへのテナント列（`white_label_id`等）追加が必要な可能性が高い。既存の単一グローバル行をHQ設定として扱う移行を含む。**この移行は既存データを壊さないことを最優先とし、既存の単一行は移行後もHQのデフォルトとして機能させる。**
- **実装内容**: 他3タスクと同じフォールバックパターンを、テナント列追加後に適用。
- **テスト内容**: 移行後も既存のCloudflare連携機能が現状通り動作すること、加えて3パターンのフォールバックを確認。
- **完了基準**: 既存機能に影響を与えず、WL単位の設定が可能になる。
- **前提タスク**: Task 1-1, 1-2, 1-3（最もスキーマ変更を伴うため最後に実施し、他タスクで固めたパターンをそのまま適用する）
