# Phase 1 詳細計画: 設定解決パターンの統一

`07_IMPLEMENTATION_ROADMAP.md`のPhase 1を、Claude Code/Codexの1セッションで完結できる粒度のタスクに分割する。既に3階層フォールバックが実装済みの`lib/repositories/email-settings.ts:105-149`を参照実装（お手本）とし、他4機能をこれに合わせる。

## Task 1-1: AI設定の3階層フォールバック化

- **目的**: `getActiveAiSetting()`がHQ行しか見ておらず、WL単位で設定してもクライアントに反映されない不具合を修正する。
- **対象ファイル**: `artifacts/flowrev/lib/repositories/ai-settings.ts`（`33-57`行付近）
- **新規ファイル**: なし
- **DB変更**: なし（既存テーブルに既にWL単位のユニーク制約があるため）
- **実装内容**: `email-settings.ts`の`getActiveEmailSetting(whiteLabelId)`と同じ構造で、クライアントID→WL ID→HQの順に検索する関数に書き換える。呼び出し元のシグネチャ変更が必要な場合は全呼び出し箇所を洗い出して更新する。
- **テスト内容**: (a) クライアント単位のAI設定がある場合それが使われる (b) クライアント単位がなくWL単位がある場合それが使われる (c) どちらもない場合HQ設定が使われる、の3パターンを確認。
- **完了基準**: 3パターンすべてで期待通りの設定が返る。既存のAI生成機能が壊れていない。
- **前提タスク**: なし

## Task 1-2: LINE設定の3階層フォールバック化

- **目的**: LINE設定がクライアント単位のみでWL単位のフォールバックがない状態を解消する。
- **対象ファイル**: `artifacts/flowrev/lib/repositories/line-settings.ts`（`47-70`行付近）
- **新規ファイル**: なし
- **DB変更**: 必要に応じて`line_settings`にWL単位のレコードを許容する列/制約があるか確認し、なければ追加を検討（既存スキーマ調査が前提）。
- **実装内容**: Task 1-1と同じフォールバックパターンを適用。
- **テスト内容**: Task 1-1と同様の3パターン。
- **完了基準**: 3パターンで期待通りの設定が返る。既存のLINE配信機能が壊れていない。
- **前提タスク**: Task 1-1（同一パターンの実装経験を踏まえて進める方が手戻りが少ないための順序づけであり、技術的な依存はない）

## Task 1-3: Stripe設定の3階層フォールバック化

- **目的**: Stripe設定がクライアント単位のみでWL単位のフォールバックがない状態を解消する。
- **対象ファイル**: `artifacts/flowrev/lib/repositories/stripe-settings.ts`（`47-70`行付近）
- **新規ファイル**: なし
- **DB変更**: Task 1-2と同様、既存スキーマ調査を前提に必要なら列/制約追加。
- **実装内容**: 同上パターン適用。**決済に関わるため、フォールバック順序の誤りが誤課金につながらないよう特に慎重にテストする。**
- **テスト内容**: 3パターンに加え、Checkout実行時に正しいStripeアカウント/キーが使われることを確認。
- **完了基準**: 3パターンで期待通りの設定が返り、実際の決済フローで誤ったアカウントが使われないことを確認。
- **前提タスク**: Task 1-1, 1-2

## Task 1-4: Cloudflare設定の3階層フォールバック化

- **目的**: Cloudflare設定がテナント概念自体を持たず全体で1行のみの状態を、テナント単位に対応させる。
- **対象ファイル**: `artifacts/flowrev/lib/repositories/cloudflare-settings.ts`（`60-82`行付近）
- **新規ファイル**: なし
- **DB変更**: `cloudflare_settings`テーブルへのテナント列（`white_label_id`等）追加が必要な可能性が高い。既存の単一グローバル行をHQ設定として扱う移行を含む。**この移行は既存データを壊さないことを最優先とし、既存の単一行は移行後もHQのデフォルトとして機能させる。**
- **実装内容**: 他3タスクと同じフォールバックパターンを、テナント列追加後に適用。
- **テスト内容**: 移行後も既存のCloudflare連携機能が現状通り動作すること、加えて3パターンのフォールバックを確認。
- **完了基準**: 既存機能に影響を与えず、WL単位の設定が可能になる。
- **前提タスク**: Task 1-1, 1-2, 1-3（最もスキーマ変更を伴うため最後に実施し、他タスクで固めたパターンをそのまま適用する）

## Task 1-5: 動作確認・回帰確認

- **目的**: Phase 1全体の変更が既存の会員サイト・決済・AI生成・メール・LINE配信機能に悪影響を与えていないことを確認する。
- **対象ファイル**: なし（確認作業のみ）
- **実装内容**: 主要フロー（購入→決済→フォロー配信→AI生成）を一通り手動確認。typecheck/build/既存テストを実行。
- **完了基準**: typecheck・buildが成功し、主要フローが従来通り動作する。
- **前提タスク**: Task 1-1〜1-4すべて完了後
